The client now refuses a monitor name or a channel label holding a control character, a line break or a direction override before sending it: U+0000-001F, U+007F-009F, U+2028-2029, U+202A-202E and U+2066-2069, exported from `cronheart/api` as `NAME_FORBIDDEN_RANGES`. `api.monitors.create`, `api.monitors.update`, `api.channels.create`, `api.channels.rename`, `defineMonitors` and the commands built on them reject such a value with `ApiInvalidRequestError` (a `SyncConfigurationError` in a configuration), naming the field and the first such code point as `U+XXXX`, and never the value; a configuration's refusal labels the monitor with those characters spelled out the same way. `cronheart init` checks `--name` before it prints or sends anything, and a name typed at its prompt before it creates a monitor, writes the env file or checks in (with an API key, the account's channels are read before the prompt), whichever way the id arrives, and exits with the usage code: a name shaped like an id is refused as it is behind `--name`, and a name outside 2-120 characters is refused as the API does, now also alongside `--uuid` and `--print-env`. `cronheart sync` now names a monitor whose name is shaped like an id, once its refused characters are set aside, by its last four characters in its plan, its result, its deletion notice and its refusals, two monitors of one name or one variable included, where `SyncConfigurationError.monitor` holds that label and the variable such a name screams is left out. A refused character in a channel label or reference that the plan, the result, `cronheart init` or a refusal prints, and in a `--uuid` or `--name` the command line echoes back, is spelled out the same way, and a sync refusal over the service's validation lists only plain field names. The check runs after the value is found to be a string and before its blankness and length, so a name of two line breaks is reported as holding U+000A. The wire contract states the set on both fields.
